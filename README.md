# OilCoin Islands — нефтяной остров, PvE/PvP и учебный блокчейн

OilCoin — серверная игра на Python/Flask и SQLite. Игрок строит остров на сетке, прокладывает трубы, распределяет нефть между производственными линиями, собирает ресурсы и открывает сундуки с картами. На арене два реальных игрока сражаются онлайн: две линии, башни, эликсир и колода. Развитие базы и торговля связывают игру с **собственным блокчейном OIL**: подписанные платежи попадают в очередь, а фоновый узел подтверждает их настоящим Proof-of-Work.

Это один управляемый учебный сервер. OIL не имеет реальной денежной стоимости, карты не являются NFT. Здесь нет внешней криптобиржи, Ethereum, независимой P2P-сети или внешних майнеров. Ключи кошельков хранит и использует сервер. Игра многопользовательская, но её блокчейн централизован: эти два свойства различаются.

## Что реализовано

- Автоматический PoW: один блок на узел не чаще раза в 30 секунд; подписи Ed25519, SHA-256, проверка истории, резерв исходящих платежей, ограниченная эмиссия и сжигание половины комиссий.
- Остров 8×8 с расширением до 10×10 и 12×12; перетаскивание, подсветка допустимых клеток, рисование труб, отмена, масштабирование и инвентарь.
- Пять улучшаемых зданий и магазин дополнительных вышек, мастерской, катализатора, компрессора, складов и энергоцентра. До пяти строителей; улучшения применяются автоматически.
- Независимые автоматические линии топлива и деталей по заданным процентам нефти. Подключение трубами влияет на производство; вне игры учитывается до восьми часов.
- Восемь взрослых anime-персонажей, четыре редкости, три сундука (премиальные за OIL), уровни и ветки развития карт, шесть карт в колоде и четыре в руке.
- PvE-кампания: 12 этапов, три промежуточных босса, ежедневное испытание с уникальными аватарами; единая боёвка и анимации действий.
- Настоящий PvP двух игроков: общий подбор или приватная комната, 120 секунд боя, серверный расчёт, восстановление после переподключения, энергия и ограниченные награды.
- Рынок ресурсов за OIL с резервом товара и доставкой после блока; периодический NPC-караван с конечными запасами и собственным кошельком.
- Anime chibi-советники, обучение в пять шагов, 12 базовых и 3 наградных аватара, рейтинг PvP, мощь базы и XP. Прогресс прежней кампании сохранён отдельно.
- Постоянная SQLite, миграция схем 1–4 в 5, резервное копирование, Docker Compose с web и worker, Gunicorn, HTTPS через nginx.
- Публичная документация на сайте: поиск, разделы, оглавления, исходный Markdown и печать. Без внешних CDN.

Тесты используют временные базы и не требуют `.env`. На Windows активируйте окружение командой `.venv\Scripts\Activate.ps1`. Для обычного запуска приложения используйте Docker по следующей инструкции; устройство кода и правила изменений описаны в `DEVELOPMENT.md`.

## Быстрый запуск через Docker

Нужны Docker Desktop на macOS/Windows либо Docker Engine с Compose plugin на Linux. Docker должен быть запущен; для образа и служебных файлов оставьте несколько гигабайт свободного места. Команды выполняются **в каталоге проекта**, рядом с `compose.yaml`.

```bash
cp .env.example .env
openssl rand -hex 32
```

Вставьте полученную строку в `.env` после `SECRET_KEY=`. Сам секрет не публикуйте. Значения `COOKIE_SECURE=false` и `ENABLE_DEMO=false` подходят для локального HTTP. Если `openssl` недоступен, создайте секрет командой `python -c "import secrets; print(secrets.token_hex(32))"`.

```bash
docker compose config --quiet
docker compose up --build -d
docker compose ps
docker compose logs --tail=100 app worker
```

Откройте **[http://localhost:8080](http://localhost:8080)**. При первом старте приложение само создаёт схему SQLite и начальный блок. В `docker compose ps` должны быть **два healthy-сервиса**: `app` обслуживает HTTP, `worker` добывает блоки, завершает стройки и рассчитывает бои. Worker запускается после успешной проверки app; ему нужен тот же том и SECRET_KEY. Условие `service_healthy` используется по [документации Compose](https://docs.docker.com/compose/how-tos/startup-order/). Проверка доступности:

```bash
curl --fail http://127.0.0.1:8080/health
```

Данные находятся в `/data/oilcoin.db` внутри контейнера и в именованном томе `oilcoin_oilcoin_data` на хосте. Пересборка образа и перезапуск контейнера сохраняют данные.

```bash
docker compose stop             # остановить, сохранив контейнер и данные
docker compose start            # запустить снова
docker compose down             # удалить контейнер и сеть; том останется
docker compose up -d            # создать контейнер с прежними данными
```

**Не запускайте `docker compose down -v`, если данные нужны:** флаг `-v` удаляет том с цепочкой и кошельками. Перед любым обновлением сделайте резервную копию.

На Windows команды `cp` и `curl` можно выполнять в WSL/Git Bash. В PowerShell скопируйте файл через `Copy-Item .env.example .env` и открывайте health URL в браузере; далее команды Docker одинаковы.

## Первая игровая сессия

1. Зарегистрируйтесь, сохраните адрес кошелька и пароль. Откроется остров с пятью зданиями, 60 нефти, 20 топлива, 120 деталями и 12 нефти в накопителе.
2. Нажмите «Собрать всё». В магазине купите трубы, в редакторе соедините вышку с переработкой. На вкладке «Потоки» задайте долю топлива; мастерская создаёт отдельную линию деталей.
3. Оставьте базу открытой: worker добывает блоки и чередует получателей награды среди активных игроков. OIL нужен для улучшения штаба и торговли. Добыча монет не расходует сырую нефть.
4. Оплатите улучшение. Следующий блок запускает таймер; готовый уровень применится сам. Штаб 2 открывает рынок и первое расширение.
5. Начальная колода уже готова к бою. Откройте «Кампания» и пройдите «Высадку»: это обучение против бота. На уровне карты 2 выберите ветку, на 3 — финальный талант. Для первого PvP сундук не обязателен. Создайте комнату на арене и передайте код второму игроку; выберите карту, затем линию. Награды, карточные роли и ограничения описаны в [правилах](docs/ISLANDS.md).

## Переход со старой версии

Используется **схема SQLite 5**. При старте схемы 1–4 расширяются атомарно без удаления блоков, аккаунтов, ресурсов, декора, сделок и XP. В версии 5 добавляются `pve_matches`, `pve_rewards`, `chest_orders`; билды и наградные аватары расширяют JSON профиля без сброса карт. Сохраняются профили островов, инвентарь, карты, очередь/матчи арены, дневные награды, NPC и состояние worker. Индекс одной стройки заменяется ограничением одной стройки каждого здания; число одновременно занятых строителей проверяет сервер.

Перед обновлением остановите оба процесса и сделайте backup вместе с исходным `SECRET_KEY`. Старые производственные задания доставляются после готовности автоматически. Уже накопленный прогресс кампании сохраняется; основной интерфейс использует онлайн-PvP и новую кампанию из 12 этапов. Ручное создание новых партий отключено. Для отката нужен старый код **и его снимок БД**; предыдущая версия не должна открывать схему 5. Переход не требует регистрации заново.

## Настройки

Compose читает `.env` автоматически. Сам Flask при запуске без Docker **не загружает `.env`**: переменные нужно экспортировать в окружение процесса.

| Переменная | Значение / назначение |
|---|---|
| `SECRET_KEY` | Случайный секрет Flask-сессий, минимум 32 символа. Обязателен в production. Также шифрует приватные ключи кошельков. Потеря или смена без миграции делает старые ключи недоступными. |
| `APP_PORT` | Порт хоста, по умолчанию `8080`; доступен только на `127.0.0.1`. Используется Compose. |
| `DATABASE_PATH` | Путь SQLite. Compose задаёт `/data/oilcoin.db`; при запуске Python задавайте отдельный доступный для записи путь. |
| `MINING_DIFFICULTY` | Начальная сложность новой цепочки, от 1 до 4, по умолчанию `3`: столько начальных шестнадцатеричных нулей требуется в хеше. |
| `ENABLE_DEMO` | `false` по умолчанию. `true` включает известные учебные аккаунты и генератор данных. Для публичного сервера оставляйте `false`. |
| `COOKIE_SECURE` | `false` для локального HTTP, `true` для сервера с HTTPS: браузер отправляет cookie сессии только по HTTPS. |
| `TRUST_PROXY` | `false` локально; `true` только за доверенным nginx, который заменяет X-Forwarded-For и X-Forwarded-Proto. Приложение доверяет ровно одному прокси. |
| `ALLOW_MANUAL_MINING` | По умолчанию `false`; Compose фиксирует `false`. Только для отдельной локальной лабораторной проверки можно экспортировать `true`; этот режим обходит игровой интервал блоков и не подходит для публичной экономики. |
| `APP_ENV` | В Docker задано `production`; локальная разработка использует `development`. |

Параметры существующей цепочки хранятся в базе: изменение `MINING_DIFFICULTY` не является способом переписать правила уже добытых блоков. Повышение сложности на 1 увеличивает ожидаемую работу примерно в **16 раз**; для демонстрации достаточно 3. Майнинг использует CPU сервера, а не браузера.

Gunicorn запускается с **одним web-процессом и четырьмя потоками**. Отдельный `python worker.py` выполняет фоновую работу раз в секунду. Каждый запрос к игровым страницам и API загружает проверенную цепочку из SQLite, а изменения выполняются внутри `BEGIN IMMEDIATE`: другие записи ждут завершения транзакции, включая майнинг. Используйте штатную пару app + worker с локальным общим SQLite-томом. Блокировка и сохранённое время последнего блока не позволяют двум фоновым шагам выдать награду за один интервал, но горизонтальное масштабирование и распределённое хранение не реализованы. Полная проверка истории на каждом запросе ограничивает пропускную способность длинных цепочек.

## Развёртывание на VPS: Ubuntu 24.04, Docker, nginx, HTTPS

Нужны VPS с SSH, доменное имя с A-записью на IP сервера и доступ к портам 80/443. Для небольшой учебной демонстрации можно начать с 1–2 vCPU и 1–2 ГБ RAM; подходящая нагрузка зависит от сложности и размера цепочки. Далее `oilcoin.example.com` замените своим доменом. Команды сервера выполняются по SSH.

### 1. Установить Docker

На чистом Ubuntu установите Docker из [официального apt-репозитория](https://docs.docker.com/engine/install/ubuntu/). Если Docker уже установлен, проверьте `sudo docker compose version` и пропустите установку.

```bash
sudo apt update
sudo apt install -y ca-certificates curl nginx certbot python3-certbot-nginx
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF_DOCKER
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: noble
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF_DOCKER
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker nginx
sudo docker compose version
```

`noble` — код Ubuntu 24.04; для другой системы используйте её официальную инструкцию. Если есть конфликтующие пакеты Docker от дистрибутива, сначала выполните шаг устранения конфликтов из официальной документации. В примерах используются `sudo docker`, поэтому добавлять пользователя в привилегированную группу `docker` не требуется.

### 2. Перенести проект и запустить

На сервере создайте каталог под текущим SSH-пользователем:

```bash
sudo mkdir -p /opt/oilcoin
sudo chown "$USER":"$USER" /opt/oilcoin
```

С локального компьютера передайте исходники (без `.env`, базы, backup и виртуального окружения):

```bash
rsync -av --exclude='.env' --exclude='.venv' --exclude='data' --exclude='backups' --exclude='*.db*' --exclude='__pycache__' ./ USER@SERVER_IP:/opt/oilcoin/
```

Если исходники размещены в вашем Git-репозитории, вместо `rsync` можно клонировать его. В архиве проекта может не быть `.git` — команда `git pull` в таком каталоге не работает.

На сервере:

```bash
cd /opt/oilcoin
cp .env.example .env
chmod 600 .env
openssl rand -hex 32
nano .env
```

Укажите новый `SECRET_KEY`, оставьте `ENABLE_DEMO=false`, установите **`COOKIE_SECURE=true` и `TRUST_PROXY=true`**. Это отдельный экземпляр сети со своей базой. Для переноса старой цепочки используйте раздел восстановления ниже.

```bash
sudo docker compose config --quiet
sudo docker compose up --build -d
sudo docker compose ps
curl --fail http://127.0.0.1:8080/health
```

Порт 8080 привязан к localhost. Не публикуйте 5000/8080 наружу: браузеры должны обращаться к nginx по HTTPS.

### 3. Настроить nginx

Создайте `/etc/nginx/sites-available/oilcoin`:

```nginx
limit_req_zone $binary_remote_addr zone=oilcoin_requests:10m rate=20r/s;

server {
    listen 80;
    server_name oilcoin.example.com;
    client_max_body_size 64k;

    location / {
        limit_req zone=oilcoin_requests burst=60 nodelay;
        limit_req_status 429;
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 120s;
    }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/oilcoin /etc/nginx/sites-enabled/oilcoin
sudo nginx -t
sudo systemctl reload nginx
sudo certbot --nginx -d oilcoin.example.com --redirect
sudo certbot renew --dry-run
```

Арена опрашивает сервер примерно раз в секунду на игрока. Лимит nginx общий для IP: при демонстрации целой аудитории за одним NAT подберите его под число участников и ресурсы VPS. Это не замена проверке нагрузки.

Certbot запросит почту и принятие условий, получит сертификат и добавит HTTPS-конфигурацию. DNS должен уже указывать на сервер. Убедитесь, что firewall провайдера допускает SSH, HTTP и HTTPS. Если вы используете UFW, сначала разрешите реальный SSH-порт, затем 80/443; не включайте firewall с закрытым SSH.

Откройте `https://oilcoin.example.com`, зарегистрируйтесь, откройте базу и дождитесь автоматического блока. После установки `COOKIE_SECURE=true` вход через обычный HTTP ожидаемо не сохраняется. Проверка через localhost `/health` от cookie не зависит.

### 4. Обновление

1. Сделайте резервную копию по следующему разделу и сохраните предыдущие исходники/образ. Затем остановите оба процесса: `sudo docker compose stop app worker`. Для снимка точно на границе обновления приостановите сначала worker, создайте backup через ещё работающий app, затем остановите app.
2. Перенесите новую версию проекта, сохранив серверный `.env` и именованный том.
3. Выполните `sudo docker compose up --build -d`.
4. Проверьте `sudo docker compose ps` (оба сервиса healthy), `/health`, `/validate`, тестовый вход и автоматическое появление блока при открытой базе. Проверьте PvP двумя браузерами.

Для системных обновлений устанавливайте исправления Ubuntu и Docker регулярно. Не меняйте `SECRET_KEY` при обычном обновлении: он нужен для расшифровки существующих ключей. Обновление зависимостей приложения сначала проверяйте тестами и на копии базы. Файл `requirements.txt` фиксирует прямые зависимости; это не полный lockfile транзитивных пакетов или digest базового Docker-образа.

Настройка доверия к заголовкам соответствует [рекомендациям Flask для reverse proxy](https://flask.palletsprojects.com/en/stable/deploying/proxy_fix/). Выпуск сертификата описан в [руководстве Certbot для nginx](https://eff-certbot.readthedocs.io/en/stable/using.html#nginx).

## Резервная копия SQLite и восстановление

На VPS выполняйте команды `docker compose` из этого раздела через `sudo`, как при установке выше.

Проверка `/health` подтверждает доступность web и читаемость цепочки; здоровье worker проверяется отдельно, поскольку он запускается после app.

База содержит **зашифрованные приватные ключи кошельков и хеши паролей**. Ограничивайте права на backup, храните внешнюю копию в защищённом месте. **Сохраните также соответствующий `.env` с `SECRET_KEY` отдельно и защищённо:** без этого секрета после восстановления нельзя подписывать переводы старых кошельков. Файл не должен попадать в Git или Docker-образ. Для шифрования приватных ключей сервер использует Fernet с ключом, производным от `SECRET_KEY`; смена секрета требует отдельной миграции ключей, которой пока нет.

### Создать согласованный backup работающего приложения

Не копируйте только живой `oilcoin.db`: при WAL часть актуальных данных может находиться в дополнительных файлах. Используйте [SQLite backup API Python](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup), создающий согласованный снимок.

Локально используйте `docker`, на VPS — `sudo docker`. Все команды ниже выполняются из каталога проекта:

```bash
mkdir -p backups
chmod 700 backups
BACKUP_NAME="oilcoin-$(date -u +%Y%m%dT%H%M%SZ).db"
docker compose exec -T app python scripts/backup.py /data/backup-snapshot.db
docker compose cp app:/data/backup-snapshot.db "backups/$BACKUP_NAME"
chmod 600 "backups/$BACKUP_NAME"
docker compose exec -T app python -c "from pathlib import Path; Path('/data/backup-snapshot.db').unlink()"
```

Не запускайте два backup-процесса одновременно: пример использует одно временное имя снимка. Скрипт проверяет структуру SQLite, внешние ключи, версию схемы, валидность блокчейна и pending-пула. Он не перезаписывает существующий файл снимка. Прерванный backup может оставить `/data/backup-snapshot.db`: сначала скопируйте его, затем удалите временный снимок указанной командой. В резервную копию входят блоки, pending-пул, аккаунты, рыночные резервы, профили, очереди строительства, PvP/PvE, награды кампании и оплаты сундуков на момент снимка. Восстановленный worker досчитает таймеры; долгий простой может завершить сохранённый бой. Копию следует унести с того же VPS и периодически проверять восстановлением на отдельном экземпляре.

### Восстановить backup

Это **замена текущего состояния** выбранным снимком. Сначала сделайте копию текущей базы. Для переноса на другой сервер восстановите соответствующий `SECRET_KEY` в его `.env`. Остановите app и worker, чтобы во время восстановления не было конкурентных чтений и записей. Подставьте существующий backup в первую строку:

```bash
BACKUP_FILE=backups/oilcoin-YYYYMMDDTHHMMSSZ.db
test -f "$BACKUP_FILE"
docker compose stop app worker
docker compose run --rm --no-deps -T -v "$PWD/$BACKUP_FILE:/restore.db:ro" app python - <<'PY'
import os
import sqlite3
from pathlib import Path
from scripts.backup import verify_snapshot
verify_snapshot(Path('/restore.db'))
source = sqlite3.connect('file:/restore.db?mode=ro', uri=True)
assert source.execute('PRAGMA integrity_check').fetchone()[0] == 'ok', 'Invalid backup'
target = Path(os.environ['DATABASE_PATH'])
with sqlite3.connect(target) as destination:
    source.backup(destination)
    assert destination.execute('PRAGMA integrity_check').fetchone()[0] == 'ok'
source.close()
print('Backup restored')
PY
docker compose up -d app worker
curl --fail http://127.0.0.1:8080/health
```

Если проверка файла или восстановление завершились ошибкой, сначала устраните её; не продолжайте сценарий вслепую. Затем откройте `/validate`, проверьте высоту цепочки и вход в кошелёк. Использование backup API при остановленном приложении корректно учитывает журналы SQLite; удалять `-wal`/`-shm` вручную у работающей базы нельзя.

## Проверка работы сервера

После запуска обоих сервисов проверьте HTTP, цепочку и worker:

```bash
docker compose ps
curl --fail http://127.0.0.1:8080/health
docker compose exec worker python scripts/worker_health.py
```

Откройте `/validate`, зарегистрируйте отдельный проверочный аккаунт и оставьте остров открытым. Worker должен записать блок и начислить OIL выбранному активному игроку. Оплатите улучшение или перевод и убедитесь, что после блока платёж подтверждён.

На публичном сервере оставляйте `ENABLE_DEMO=false`: известные демонстрационные пароли предназначены для отдельных учебных экземпляров. Отключение генератора не удаляет ранее созданные демо-аккаунты. При первом развёртывании на новом VPS создаётся новая база; существующие данные переносятся отдельно через backup/restore.

## Если что-то не работает

| Симптом | Что проверить |
|---|---|
| Compose требует `SECRET_KEY` | Создан ли `.env`, заполнено ли значение, текущий ли это каталог проекта. |
| `Cannot connect to the Docker daemon` | Запущен ли Docker Desktop / служба Docker. |
| Контейнер `unhealthy` | `docker compose logs --tail=100 app worker`, `/health`, доступ к базе, длительный майнинг. |
| Не сохраняется вход | На HTTP нужен `COOKIE_SECURE=false`; на HTTPS — `true`. Очистите старые cookie после смены секрета. |
| Ошибка прав на `/data` | Используйте штатный именованный том. Для собственного bind mount каталог должен быть доступен UID/GID `10001:10001`. |
| Неверная цепочка после изменения БД | Не исправляйте хеши вручную. Остановите узел и восстановите проверенный backup. |
| Новый пустой мир после переноса | База не находится в образе. Переносите её отдельно через backup/restore; проверьте имя Compose-проекта и тома. |
| Нет автоматических блоков или бой стоит | Работает ли worker, совпадают ли DB/SECRET_KEY двух процессов, свежая ли отметка `python scripts/worker_health.py`. Без активных игроков и pending добыча приостанавливается. |
| Майнинг долго не заканчивается | Сложность растёт экспоненциально; CPU маломощного VPS и размер блока влияют на время. |
| `/demo` недоступен | По умолчанию `ENABLE_DEMO=false`; это ожидаемо. |
