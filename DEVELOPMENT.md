# Руководство разработчика

## Запуск и устройство

Основная инструкция, переменные окружения, Docker, VPS и backup находятся в [README](README.md). Подробная модель блокчейна и БД — в [ARCHITECTURE](docs/ARCHITECTURE.md). Используйте Python 3.12 и зависимости `requirements.txt`.

`create_app(config)` создаёт приложение; `app:app` — точка входа Gunicorn. В тестах задавайте отдельный `DATABASE_PATH`, тестовый `SECRET_KEY` и низкую сложность. Не направляйте проверки на рабочий Docker volume. Для локального запуска нужен каталог базы, доступный текущему пользователю; Compose использует UID/GID 10001 и `/data`.

## Работа с состоянием

`database.unit_of_work` обеспечивает общую транзакцию для вложенных вызовов через ContextVar. Соединения не следует хранить как один глобальный объект для всех потоков. `BEGIN IMMEDIATE` применяется к изменениям; ошибка приводит к rollback. При добавлении нового действия учитывайте одновременно изменения памяти и БД: SQL rollback сам по себе не откатывает произвольные Python-объекты.

`storage.load_blockchain` проверяет историю и pending-пул. `storage.save_blockchain` не позволяет сокращать цепь или заменять хеш подтверждённого блока. Не добавляйте «исправление» повреждённой базы автоматическим genesis: это потеря данных. Восстанавливайте проверенный backup.

Штатный web-сервер использует один процесс Gunicorn и четыре потока; рядом работает отдельный `python worker.py` с тем же DATABASE_PATH и SECRET_KEY. Состояние цепочки загружается в `g.blockchain` внутри транзакции запросов к игре и API, а `BEGIN IMMEDIATE` сериализует writers. Фоновый майнинг держит эту транзакцию до сохранения; увеличение workers не делает записи параллельными и не является поддержанным режимом масштабирования. Перед изменением топологии нужны отдельные проверки согласованности, нагрузки и восстановления.

## Документация на сайте

Blueprint `documentation.py` публикует `/docs/` и статьи по явно заданному каталогу `DOCUMENTS`. Источник — `README.md` и Markdown-файлы из `docs/`; второй копии текста в HTML нет. Внутренние ссылки между файлами превращаются в ссылки на статьи, заголовки получают якоря, а поиск возвращает подходящие разделы. Поиск не зависит от SQLite или сторонних сервисов и ищет все введённые слова без учёта регистра и различия «е/ё», без морфологии.

Для новой статьи создайте Markdown-файл и добавьте `Document` с уникальным slug в каталог. Используйте один начальный H1, H2/H3 для оглавления, относительные ссылки на другие руководства и код в ограждённых блоках. Поддерживаются таблицы. Raw HTML отключён; произвольный путь из URL не читается. Публикуемые изображения отдельно перечислены в `ASSETS`. Не добавляйте в каталог конфигурацию, секреты или файлы данных.

Схема из архитектуры рисуется локально в SVG; поддерживается простой ациклический граф Mermaid `flowchart LR/TD/TB` с отдельными строками `A[Подпись] --> B[Подпись]`. Неподдержанная схема останется блоком кода. Для других типов диаграмм расширьте рендерер явно. CDN и внешние скрипты не требуются.

Оформление находится в `templates/docs/`, `static/docs.css` и `static/docs.js`. Серверная навигация и поиск работают без JavaScript; он добавляет копирование кода, печать и подсветку оглавления. Markdown-текст кешируется по времени изменения и размеру файла. Локальная правка текста видна при следующем запросе; для контейнера пересоберите образ. Страницы помощи обходят загрузку цепочки при HTTP-запросе, поэтому остаются доступны, если уже работающий узел обнаружил повреждение данных. Проверка базы при старте приложения сохраняется.

`tests/test_documentation.py` проверяет публикацию публичных руководств, ссылки и якоря, скачивание, поиск, запрет исполнения HTML и чтения посторонних файлов, а также расчёт первых шагов из руководства игрока.

## Добавление игровых функций

- Денежные операции реализуйте в `blockchain.py`, а не прямой корректировкой баланса в SQL.
- Подписывайте перевод через `wallet.py` и проверяйте каноническое представление. Новые подписанные поля требуют явного решения о совместимости.
- Изменение формата хеша требует новой версии и тестовых векторов; служебные поля не добавляйте в хеш без причины.
- Игровые бонусы оформляйте событиями с уникальным `event_key`, чтобы повторный запрос не начислял их дважды.
- Привязывайте покупку к `tx_id`, а активацию — к подтверждению в блоке.
- Любое изменение через HTTP делайте POST с авторизацией и CSRF. Отправитель берётся из сессии.
- Не возвращайте `password_hash` или `encrypted_private_key` через API и шаблоны. Зашифрованный ключ также является секретным материалом.
- Изменения схемы оформляйте миграцией с backup и явной версией; `CREATE TABLE IF NOT EXISTS` не мигрирует структуру старой таблицы.

## Проверки

Для разработки создайте отдельное окружение и установите тестовые зависимости:

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

Тесты сами создают временные базы; `.env` для них не нужен. На Windows активируйте окружение командой `.venv\Scripts\Activate.ps1`.

Демонстрационные данные создаются только при явном `ENABLE_DEMO=true` командой `python scripts/seed_demo.py`. Используйте отдельный `DATABASE_PATH` и учебный экземпляр: пароли demo-аккаунтов публичны. Скрипт расчёта экономики запускается через `python scripts/economy_report.py`.

Для проверок клиентского JavaScript нужен Node.js; дополнительных npm-пакетов нет:

```bash
node tests/client_regressions.cjs
```

Эти проверки воспроизводят длительный опрос кампании, построение графика для большой истории и завершение стройки при несохранённых долях производства. Серверные регрессии аудита находятся в `tests/test_audit_regressions.py`.

Тесты должны проверять инварианты: отклонение подменённой подписи/суммы, завышенной награды, неправильной комиссии, двойной траты, повторного идентификатора, повреждённой цепочки; сохранность после повторной загрузки; авторизацию и CSRF; подтверждение улучшений и однократность XP.

При изменении интерфейса дополнительно пройдите сценарий регистрации → автоматический блок → перевод → подтверждение → Explorer, а также матч двух браузерных сессий и редактор труб на ширине телефона и настольного экрана. Проверьте длинные адреса, пустую историю и ошибки форм. Автоматические тесты сервера не заменяют проверку внешнего вида.

Проверка Compose без запуска Docker daemon:

```bash
docker compose config --quiet
```

Далее отдельно нужны сборка образа, healthcheck, запись в `/data`, рестарт с сохранением кошелька и backup/restore. Не называйте сборку/деплой успешными только по наличию конфигурации.

## Исторические данные

Legacy v1/v2-форматы блоков имеют отдельные правила хеширования. Совместимость вычисления хеша не означает, что старый неподписанный перевод становится допустимым в новой подписанной сети. Старый мигратор `migrations/001_add_block_versions.py` сохраняет backup перед изменением отдельного legacy JSON-файла; он не используется для обновления SQLite. Автоматического импорта старых JSON-аккаунтов в новую базу нет: у них отсутствуют корректные новые ключи/подписи. Держите старые данные отдельно.

## Модель острова и миграция схемы 5

`database.initialize` принимает схемы 1–5 и атомарно добавляет недостающие таблицы. Переход 4→5 добавляет таблицы PvE и OIL-сундуков. Предыдущая миграция 4 снимает старый индекс единственного строителя и добавляет уникальность незавершённого улучшения `(address,kind)`. Число параллельных jobs проверяется по числу нанятых строителей. Кошельки, блоки, ресурсы, старые jobs и рынок сохраняются. Неизвестная версия отклоняется. Для отката восстанавливайте снимок вместе с кодом и SECRET_KEY соответствующей версии.

`district._read` вызывает чистую проекцию `colony.project`: серверные десятисекундные интервалы добычи, целочисленные дробные остатки, дневная квота, восьмичасовой предел, независимые выходы и энергия. GET не сохраняет начисление; POST и worker фиксируют его через `_save`. Сначала проецируйте старое состояние, затем меняйте доли, уровень, планировку или ускоритель. Иначе бонус мог бы распространиться на время до покупки. Нельзя заменять это клиентским таймером.

`colony.network` обходит соседние трубы BFS от краёв размещённых вышек. Фабрики подключаются к достигнутым трубам, но не служат мостом сети. Инвентарь хранит общее купленное количество, размещение использует часть этого количества. Удаление купленного объекта с сетки не уменьшает владение. Основные пять зданий обязательны, декор не возвращает расходы.

## Фоновый процесс и восстановление

`worker.py` вызывает один `engine.step` в секунду. Внутри `BEGIN IMMEDIATE`: проекции активных профилей, готовые стройки, старые партии, матчи, подбор ожидающих игроков, затем при необходимости автоматический блок. Запись `runtime_state.last_block_at` предотвращает повторную награду в одном интервале, `last_miner` задаёт круг получателей. После долгой остановки нет выпуска за каждый пропущенный интервал. Для активных стройки и арены браузер не обязан оставаться открытым.

`engine.finish_ready` применяет несколько готовых построек по их job_id и только один раз. Начало таймера связано с включением оплаты в блок через `district.confirm_construction`. `market.settle` проверяет подписанный платёж и доставляет товар до общего commit. CLI-код, который меняет цепочку, должен делать эти операции в общей транзакции.

В Docker у Gunicorn указан `--no-control-socket`: служебный сокет управления не нужен, а домашний каталог контейнера недоступен для записи. Доступный временный каталог web — `/tmp`. При SIGTERM worker завершает текущий шаг; Compose даёт 130 секунд. `scripts/worker_health.py` требует heartbeat младше 20 секунд. Не вызывайте рабочий цикл из Gunicorn-потоков и не запускайте автоматический поток при импорте `app.py`: несколько процессов могли бы непредсказуемо конкурировать. Отдельный worker стартует явной командой.

## Карты, онлайн-арена и повторные запросы

`arena.py` содержит каталог персонажей, вероятности, состав сундуков и серверную симуляцию. Сундук использует `secrets` и уникальный `(address,request_id)`. Шансы объявлены игроку; это серверная случайность, без on-chain доказательства генерации. Колода — шесть уникальных открытых карт; уровни и порядок копируются в матч при старте.

Бой хранится в `arena_matches.state`, статус — отдельное индексированное поле. `advance` обрабатывает оставшиеся секунды по серверному времени, не повторяя уже записанные. Урон и перемещения вычисляются от одного снимка шага. POST play сверяет `hand_revision`; reward фиксируется в той же транзакции со статусом finished. Подбор приватный по коду или публичный по трофеям; worker расширяет диапазон через 30 секунд, даже когда новые участники больше не приходят. Очередь истекает без heartbeat через 45 секунд.

Интерфейс `static/arena.js` опрашивает JSON раз в секунду, обновляет отряды и руку без полной перезагрузки. Ответ старого GET не должен затирать более свежий POST: клиент сравнивает поколение запроса. При потере связи не определяйте исход на клиенте; восстановите серверное состояние.

## Расширение рынка и редактора

`layout.py` проверяет координаты, footprint, купленный инвентарь, пересечения и revision до списания декора. `static/editor.js` отвечает за drag/tap, рисование, подсветку, отмену и масштаб, но не является источником истины. `static/colony.js` обновляет производство и строительные таймеры.

`market.py` хранит цену/комиссию в атомарных units, ресурс в резерве, tx_id и переходы open → pending → filled. Исходящий товар и ожидающие покупки учитываются `market.held` в занятости склада. Ошибка записи блока откатывает и доставку. `npc.py` использует этот же механизм, конечный кошелёк и SAVEPOINT для отката составной сделки при бизнес-ошибке. Не добавляйте NPC бесконечную эмиссию или безусловный выкуп.

`python scripts/economy_report.py` считает верхние границы и отдельно старую кампанию, не предсказывает спрос. Новые правила покрываются `tests/test_colony_arena.py`, рыночные инварианты — `tests/test_market_layout.py`. Проверяйте смену UTC-дня, частый/редкий опрос, конкурентный подбор, повтор хода/сундука/награды, скрытие чужой руки, rollback и восстановление незавершённого матча из backup.

## Иллюстрации и интерфейс

Атласы `static/art/cards-atlas.png` (4×2) и `static/art/advisers-atlas.png` (4×1) созданы встроенным image_gen. Картинки подключаются локально, портреты выбираются CSS background-position. Боевые персонажи явно взрослые 26–34 лет; chibi-советники отдельные несексуализированные персонажи. Здания — собственные SVG в `templates/game/_art.html`.

При изменениях одновременно обновляйте интерфейс, серверные правила, ISLANDS/ECONOMY и проверки. Не меняйте odds или стоимость только в шаблоне. После редактирования проверьте телефон, планшет и настольный экран, отсутствие горизонтального переполнения и ошибки консоли; отдельно сыграйте матч двумя сессиями.

## Расширения версии 5

Новые модули: `campaign.py` (PvE и уникальные награды), `card_builds.py` (таланты и итоговые характеристики), `chests.py` (котировки, платежи и доставка). Схема 5 добавляет три таблицы без удаления существующих. Меняя характеристики, проверяйте общий `arena._step`: он используется обоими режимами. В матч копируются готовые stats, чтобы последующая смена билда не меняла начавшийся бой.

Тесты `test_campaign_chests.py` покрывают прогрессию, дневной ключ, способности, параллельный старт, снимок билда, платежи/доставку, восстановление worker, миграцию 4→5 и частичный сбор. После изменения схемы обновляйте также `scripts/backup.py`; он не импортирует Flask-приложение и проверяет платежи сундуков по блокчейну. [Полные игровые правила](docs/CAMPAIGN.md).
